⑥ Virtuoso 匯入與匯出

接手的人常用 Cadence Virtuoso 開版圖、再交給 Siemens Calibre 做 DRC。這一段在 WSL 中裝有這兩套工具的 Linux 環境裡，以批次模式（不開視窗）實際走一次：

  1. XStream In（strmin）：把簽核版 GDS 匯入成 Virtuoso 的 OA library。沒有 CORNERSTONE 的 Virtuoso 製程套件，所以用自動圖層對應（GDS 3 → L3 drawing，其餘類推）。OA library 放在 Linux 原生目錄，不放在 Windows 掛載目錄。
  2. 讀 OA：用一段 SKILL（virtuoso -nograph -replay）數 cell、instance、各層圖形與多邊形的最大點數，確認匯入內容完整。
  3. XStream Out（strmout）兩次：一次用預設值，一次加 -maxVertices 8191 -dbuPerUU 1000。
  4. 兩個匯出檔都與簽核版逐層做 XOR（互斥或），並各跑一次 KLayout pre-DRC。

預設匯出為什麼會多出線寬違規

預設匯出用垂直線把 15 條超過 200 點的曲線切開，GDS 3 從 51 塊變成 80 塊，多出 29 條接縫。接縫上的新頂點取整到 1 nm 格點，所以和原形狀有極小差異（XOR 共 0.0091 µm²，分散在 20 塊）。KLayout pre-DRC 在其中 8 條接縫上各報 2 個 GDS 3 線寬違規，共 16 個；Calibre 對同一個檔案報 0。

標記的兩條邊一條是切線、一條是波導邊，表示 KLayout 是一塊一塊量的，沒有先把同層的多邊形合併。用同一份檔案做對照實驗：

KLayout 的寫法（GDS 3 線寬 < 0.349 µm、夾角限制 45°）標記數
先合併再量（.merged.width）0
剛讀進來的圖層直接量（預設會合併）0
逐塊量（.raw.width）16
照平台規則檔的順序：先對同一層呼叫 .raw.sized(0.2.um)，再量線寬16

原因在平台規則檔：檢查 GDS 60 與 GDS 3 重疊的那一行寫了 soi_etch2_light_layer.raw.sized(0.2.um)。.raw 會直接把這個圖層物件改成「不合併」模式，所以後面 GDS 3 的線寬與間距檢查都是逐塊量。Calibre 讀圖層時一律先合併，接縫消失，只剩不到 1 nm 的折角，所以是 0。平面模式與階層模式結果相同（表中為階層模式）。

標記的邊長 0.51–0.70 µm，位置（µm）：(-760, -206.3)、(-760, 69.4)、(-760, 293.7)、(-660, -181.4)、(-660, 100.6)、(-660, 318.6)、(2256, -340.2)、(2256, 219.6)。這些接縫都落在波導坡度大於 45° 的地方：切線與波導邊的夾角小於 45°，才在夾角限制的檢查範圍內；緩坡上的接縫夾角大，不被檢查。修正：匯出時加 -maxVertices 8191，每條曲線維持一塊，幾何與簽核版完全相同，兩個引擎都是 0。送件或交給別人時，要用 log 確認實際用了哪個 maxVertices。

⑦ Calibre DRC 對照

CORNERSTONE 只提供 KLayout 規則檔。這裡把它逐條改寫成 Calibre 的 SVRF（cornerstone_pre_drc.svrf），以 calibre -drc -hier 批次執行，再和 KLayout 逐條比較。改寫原則：

  • 門檻與 KLayout 版相同（規則值減 0.001 µm）；KLayout 的 angle_limit(45) 寫成 ABUT < 45，兩者都用歐氏距離。
  • 只改寫本設計用到的圖層（GDS 3、4、5、39、41、99、100）。GDS 6、60 的規則沒有改寫，改成「這兩層只要出現圖形就報錯」，不會因為沒改寫而漏掉。
  • 設計區面積由執行時傳入（VARIABLE DESIGN_AREA），與 KLayout 的 dw、dh 相同。

同一批輸入兩個引擎都跑：簽核版、兩個 Virtuoso 匯出版、M2 s6 的規則故障檔（每條規則一個違規）、把設計區宣告少 100 µm、以及 M3 s2 的 11 個邊界案例。

⑩ 判讀練習

題目怎麼做要寫出的結論
1. 為什麼不比 SHArebuild_gds.py 為什麼比多邊形，不直接比 SHA-256？GDS 檔頭記錄寫出的時間，同樣的幾何每次寫出的位元都不同；比多邊形才是比「設計內容」。交付檔本身則用 SHA-256 鎖定。
2. 三支程式的分工check_delivery、verify_gds、rebuild_gds 各證明什麼？檔案沒被改過；版圖的接法與規格一致；版圖確實由附上的程式產生。三者缺一，交付都不完整。
3. 相位表能直接用嗎拿 simulation/phase_settings.json 的 θ、φ 直接設定 heater 可以嗎？不行。那是弧度，heater 要的是電壓或電流；要先量每個 heater 的電壓 → 相位關係，也要把晶片製作後的固定相位一起校正。
4. 交付包要給誰量測人員最先打開哪三個檔案？README、optical_ports.csv、pad_map.csv：先知道晶片做什麼，再對準光纖、排探針。
5. 同一個檔案兩個答案預設匯出的 GDS，KLayout 報 16 個線寬違規、Calibre 報 0。哪個對？送件要怎麼做？兩個引擎都照自己的規則正確執行：Calibre 先把同層多邊形合併再量，合併後只剩不到 1 nm 的折角；平台規則檔因為前面呼叫了 .raw，GDS 3 改成逐塊量，接縫上的尖角就被當成線寬不足。送件以平台規則為準，所以要用 -maxVertices 8191 匯出，讓每條曲線維持一塊。
6. 為什麼只有部分接縫被標記預設匯出多出 29 條接縫，為什麼只有 8 條有標記？XStream 用垂直線切開曲線。波導在接縫處越陡，切線和波導邊的夾角越小；坡度超過 45° 時夾角小於 45°，落在 angle_limit(45) 的檢查範圍內才會被量到。緩坡上的接縫夾角大，不被檢查。
7. 改寫規則檔的風險Calibre 版和 KLayout 版在規則故障檔與邊界案例完全一致，可以拿 Calibre 版取代平台規則檔嗎？不行。第 5 題就是兩者語意不同的實例；GDS 6、60 的規則也沒有改寫。Calibre 版只能當第二道檢查，簽核仍以平台規則檔與 CORNERSTONE 的完整 DRC 為準。

⑪ 限制

  • 重建需要授權：rebuild_gds.py 需要 IPKISS 與 CORNERSTONE PDK；沒有授權的接手者只能做 check_delivery 與 verify_gds。
  • DRC 規則檔不在包內：要向 CORNERSTONE 取得；包內附原始 DRC 報告（.lyrdb）供對照。
  • 原始碼的路徑：打包時把本機的絕對路徑改成相對說明，其餘內容與課程程式相同；完整重跑整個課程需要課程的資料夾結構與各步的輸出。
  • Virtuoso 沒有製程套件：用自動圖層對應匯入，沒有 CORNERSTONE 的 Virtuoso 技術檔與元件辨識，所以只驗證匯入、匯出與幾何，不在 Virtuoso 裡做 DRC 或 LVS。
  • Calibre 規則檔是自行改寫的：不是平台發行的版本；GDS 6、60 的 10 條規則沒有改寫（本設計不用這兩層，以「出現就報錯」防守）；合併語意與平台規則檔不同（見 ⑥）。
  • 沒有做 Calibre LVS：光子元件的 LVS 需要元件辨識規則，PDK 沒有提供；光學 LVS 仍以 M2 s6 只讀 GDS 的檢查為準。
  • 只用批次模式：沒有操作 Virtuoso 與 Calibre 的圖形介面（Calibre Interactive、RVE）；結果以 log、summary 與 ASCII 結果檔為準。
  • 需要授權環境：⑥、⑦ 要在裝有 Cadence、Siemens 工具與授權的 Linux 環境執行，不在 M3 s1 的從零重建範圍內。交付包不變：8191 點匯出檔與簽核版幾何相同，交付仍以簽核版為準。
  • 其餘限制同 M2 s5、s6：EC 未模擬耦合、損耗與熱模型未建、pre-DRC。
